# PR review

Ревью изменений в skill-atlas по четырём измерениям: **функционал**, **перфоманс**,
**секьюрити**, **код-стайл проекта**. Аргументы: `$ARGUMENTS`.

## 1. Что ревьюим

- Число → PR: `gh pr view <N> --json number,title,body,headRefName,baseRefName,url,files`
  и `gh pr diff <N>`. Локальная ветка может отставать, поэтому код читай через
  `git fetch origin pull/<N>/head:pr-<N>` и `git show pr-<N>:<path>`, рабочее дерево не трогай.
- Имя ветки → `git diff main...<branch>`, если для ветки есть PR (`gh pr view <branch>`),
  то возьми из него описание.
- Пусто → текущая ветка против `main` (`git diff main...HEAD`) плюс незакоммиченные изменения
  (`git diff HEAD`). Если ветка `main` и изменений нет — скажи об этом и остановись.
- `--comment` → в конце опубликовать ревью в PR (см. шаг 5).

Собери: список изменённых файлов, полный diff, описание PR (разделы «Спека», «Тесты»,
«Риски» из `.github/pull_request_template.md`), статус CI (`gh pr checks <N>`, если есть PR).

## 2. Контекст проекта

`README.md` — спецификация и Definition of Done. Прочитай целиком: каждое изменение
поведения проверяется против него. Изменённые файлы читай целиком, не только hunks.

Параллельно с ревью запусти в фоне `./gradlew build -q` (Bash с `run_in_background`)
на ревьюируемой ревизии: если ревьюишь не текущее рабочее дерево, собери в отдельном
worktree (`git worktree add /tmp/skill-atlas-review-<N> pr-<N>`), а в конце удали его.

## 3. Ревью — 4 параллельных субагента

Запусти четыре `Agent` (subagent_type `reviewer`, если доступен, иначе `general-purpose`)
**в одном сообщении**. Каждому передай: путь к репо, как получить diff (точная команда),
список файлов, описание PR, его чек-лист ниже и формат ответа:

```
[CRITICAL|MAJOR|MINOR] <заголовок> — <file>:<line>
Проблема: <что не так и при каком входе/состоянии ломается>
Предложение: <конкретная правка>
```

Только находки, относящиеся к изменённому коду (или к коду, который он ломает).
Без находок — так и написать. Стилистические придирки, которых нет в чек-листе, не нужны.

### Функционал

- Поведение соответствует README; если поведение изменилось — README поправлен в том же PR
  (спека → тест → код). Новые опции CLI, форматы, эндпоинты описаны в README.
- Формат отчёта — контракт: `table`, `md`, `json` меняются согласованно, обратная
  совместимость JSON (поля не переименованы и не удалены без явного решения в спеке).
- Exit codes `0..4` и маппинг ошибок в `WebServer` (404 / 429 / 502 / 400) не сломаны,
  новые ошибки попадают в правильную ветку `GitHubException`.
- Тесты: только интеграционные через `StubGitHub`, отчёт сравнивается целиком. Новое
  поведение и каждый баг-фикс закрыты тестом; корнер-кейсы из раздела README «Тесты» либо
  покрыты, либо помечены там отложенными; ⚠-отметки сняты только вместе с правкой.
- UI-изменения: обновлены Playwright-спеки (`e2e/ui.spec.ts`) и baseline-скриншоты
  для `darwin` и `linux`.
- Корнер-кейсы: пустой репо (409), `truncated` дерево, артефакт без frontmatter / без `name`,
  битый YAML, дубли, пустой ввод, регистр, ведущий `/` у команд.

### Перфоманс

- Бюджет запросов к GitHub: скан репо = 2 + 1 на артефакт. Нет лишних запросов в цикле,
  повторного получения дерева/метаданных, Contents API вместо `raw`.
- Скан организаций ограничен (`MAX_ORGS`, одна страница `OWNER_REPOS_PAGE_SIZE`), новые
  «массовые» операции имеют такой же явный лимит.
- `HttpClient` и `Json` переиспользуются, не создаются на каждый запрос внутри цикла;
  таймауты заданы.
- Алгоритмы по артефактам (похожесть — O(n²) по парам) не вызываются повторно и не растут
  хуже, чем описано в README.
- `WebServer`: обработчики не блокируют фиксированный пул из 4 потоков дольше нужного.
- Web UI: фильтрация и перерисовка на клиенте без повторных запросов к `/api/*`, без
  перерисовки всего списка на каждый символ, если это заметно на сотнях артефактов.

### Секьюрити

- Токен: только `--token` / `GITHUB_TOKEN` / CI secret. Не логируется (в т.ч. в `-v`),
  не попадает в URL, в тело ответа `/api/*`, в сообщения исключений, в отчёт, в UI.
- `WebServer` слушает только `127.0.0.1`; новые эндпоинты — только `GET`, без CORS.
- Инъекции в URL: `owner`, `repo`, `ref`, `path` подставляются в URL GitHub — проверь
  валидацию (`parseRepo` / `parseOrg`) и что `ref` / `path` из пользовательского ввода
  не дают `../`, `?`, `#` и переход на другой хост.
- XSS в `index.html`: `name`, `description`, `path`, `error` приходят из чужих репозиториев.
  Рендер только через `el(...)` / `textContent`, никакого `innerHTML` с данными;
  `href` — только `https://github.com/...`, не `javascript:`.
- YAML (`snakeyaml`): безопасная загрузка, без произвольных типов и тегов, лимиты на алиасы
  и размер документа (billion laughs) не ослаблены.
- Ответы GitHub: тело ошибки не пробрасывается пользователю целиком, если может
  содержать чувствительные данные.
- CI (`.github/workflows/*`): минимальные `permissions`, нет `pull_request_target` с checkout
  кода из форка, секреты не выводятся в лог.
- Нет секретов и токенов в коде, фикстурах, скриншотах, README.

### Код-стайл проекта

- Структура пакетов: `github` (HTTP-клиент и модели API), `scan` (поиск, парсинг, анализ),
  `report` (форматирование), `web` (сервер); код лежит в своём пакете.
- Стек без новых зависимостей: Clikt, kotlinx.serialization, snakeyaml,
  `java.net.http.HttpClient`, `com.sun.net.httpserver` (в т.ч. в тестах — без WireMock /
  MockWebServer). Новая зависимость — только с обоснованием в README.
- Kotlin как в проекте: ошибки — подклассы `sealed class GitHubException`; константы —
  top-level `const val` в `UPPER_SNAKE_CASE` с KDoc «почему такое значение»; expression
  bodies и `?: return` вместо вложенных `if`; trailing commas в многострочных параметрах;
  `data class` + `copy` вместо мутации; `private` для всего, что не нужно снаружи.
- Комментарии и KDoc — по-русски, кратко, объясняют «почему», а не «что». Плотность как
  в соседнем коде, без закомментированного кода.
- Мёртвого кода нет: неиспользуемые параметры, поля, импорты, зависимости удалены;
  `./gradlew shadowJar -q` без warnings.
- Тесты: без юнит-тестов на приватные методы, стиль `ScanIntegrationTest` /
  `WebServerIntegrationTest`, live-тесты помечены тегом `live`.
- Web UI: один `index.html` без сборки и внешних скриптов; хелпер `el(...)`, функции
  `render` / `renderArtifact`; цвета — CSS-переменные в `:root` с dark-mode вариантом.
- Коммиты — по-английски, повелительное наклонение, с префиксом области
  (`Web UI: …`, `Scan: …`); README и тексты задач — по-русски.

## 4. Верификация

Каждую находку проверь сам, прежде чем показывать: открой код по `file:line`, убедись, что
проблема реальна на этой ревизии и не закрыта в другом месте diff'а (валидация выше по
стеку, тест, README). Попробуй её опровергнуть. Неподтверждённые — выкинь, спорные —
оставь с пометкой «под вопросом». Дубли между измерениями — склей.

Дождись `./gradlew build`: красная сборка или упавшие тесты — отдельная CRITICAL-находка
с выводом ошибки.

## 5. Отчёт

```
## Вердикт: APPROVE | NEEDS_CHANGES | REJECT

<2–3 предложения: что делает PR и главное по результатам>

Сборка: ./gradlew build — ✅ / ❌ | CI: ✅ / ❌ / нет PR

### Функционал
- [MAJOR] … — `src/main/kotlin/…:42`
  Проблема: …
  Предложение: …
### Перфоманс
### Секьюрити
### Код-стайл

### Что хорошо
- …

Находок: N (critical X, major Y, minor Z); отсеяно при верификации: M
```

Пустое измерение — «замечаний нет». Вердикт: есть CRITICAL или красная сборка → REJECT
или NEEDS_CHANGES; есть MAJOR → NEEDS_CHANGES; иначе APPROVE.

С `--comment`: покажи пользователю текст ревью и дождись явного «ок» — публикация видна
всем. Затем запиши тело в файл и опубликуй:
`gh pr review <N> --comment --body-file /tmp/skill-atlas-review-<N>.md`
(`--request-changes` / `--approve` — только если пользователь попросил). Верни ссылку на PR.
